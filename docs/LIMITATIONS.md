# 알려진 한계 (정직하게 적어두는 것이 목적)

이 문서는 "구현된 것처럼 보이지만 실제로는 안 되는 부분"을 숨기지 않기 위해 존재한다.
발표·심사 자료에도 이 목록을 그대로 반영할 것.

## 1. IMU/터치 이벤트 위조 가능성 — 해결되지 않음 (가장 중요)

`server/test/spoof_test.js`로 실제로 검증한 결과, 페이지 JS에서
`window.dispatchEvent(new DeviceMotionEvent(...))`로 배경 잡음 + 탭 타이밍에
맞춘 burst를 흘려보내면 **융합 위험도 점수가 81 → 0으로 떨어지고 흔들기
챌린지 자체가 생략된다.** (재현: `npm run test:spoof`, 결과는
`docs/SPOOF_TEST_RESULTS.md`.)

즉, 이 시스템은 "브라우저가 보고하는 `devicemotion` 이벤트가 실제 하드웨어에서
왔다"는 가정 위에 서 있고, 그 가정은 웹 표준 API만으로는 증명할 수 없다.
근본 해결책은 이 코드베이스 밖에 있다 — Android Play Integrity API, 네이티브
앱 SDK를 통한 커널/드라이버 레벨 attestation 등. 지금은 **레이어를 늘려
공격 비용을 올리는 것**(스코어 하나만 속이면 안 되게)까지가 현실적 목표이고,
그마저도 위 테스트에서 뚫렸다는 사실을 감춰선 안 된다.

## 2. L2 시각 유사도 — CLIP은 아니지만 실제로 동작하는 버전이 있다

기획서의 핵심 아이디어("은행처럼 보이는데 은행 도메인이 아니면 피싱")를
CLIP/ResNet 임베딩으로 구현하진 못했다(이 환경에 그런 ML 런타임이 없음).
대신 `server/src/visual.js`에 지각적 해시(average hash) 기반의 가벼운
버전을 넣었다: 렌더링된 페이지 스크린샷 중앙 카드 영역을 잘라 16×16
해시로 만들고, 미리 만들어둔 "은행 로그인 화면" 레퍼런스와 Hamming
거리를 비교한다. 화이트리스트 도메인이 아닌데 레퍼런스와 매우 가까우면
(거리 ≤40/256) `looksLikeBankTemplate` 신호로 잡아 점수를 크게 올린다
(`server/src/l2.js`).

실제로 작동을 검증했다: 은행 목업과 일부러 비슷하게 만든 가짜 클론
페이지는 거리 4로 정확히 잡혔고(점수 60 → high), 관련 없는 일반 페이지는
거리 74~93으로 정확히 걸러졌다. 다만 **레퍼런스 이미지가 진짜 은행
스크린샷이 아니라 내가 직접 만든 일반적인 한국 은행 로그인 페이지
목업**이다 — 이 환경의 네트워크 정책이 실제 은행 도메인 접속을 막아서
(`kbstar.com` 등 시도해봤지만 전부 연결 실패) 진짜 화면을 가져올 수
없었다. 실제 배포 환경(네트워크 제한 없음)에서는 `server/scripts/
build_visual_reference.js`를 실제 공식 도메인(L1의 `OFFICIAL_DOMAINS`)
스크린샷으로 주기적으로 재생성하도록 바꾸는 게 다음 단계다. 지금 상태로도
"흔한 은행 로그인 레이아웃을 그대로 베낀 조잡한 클론"은 잡지만, 실제
은행 화면을 픽셀 단위로 정교하게 복제한 페이지에는 이 레퍼런스가
얼마나 잘 맞을지 검증되지 않았다.

## 3. L1/L2는 학습된 모델이 아니라 손으로 짠 휴리스틱이다

`server/src/l1.js`의 점수 가중치(`isSuspiciousTld: 15`, `brandLookalike: 45`
등)는 여전히 상식적으로 부여한 값이지 학습된 게 아니다. 다만 규칙 자체는
이제 실제 라벨링된 데이터로 검증됨: `scripts/eval_l1_model.js`가 실제
피싱 피드(mitchellkrogza/Phishing.Database, ~39만 건)와 실제 상위 도메인
목록(OpenDNS top domains, 1만 건)을 매번 새로 받아와 평가한다(`npm run
eval:l1`, 결과는 `docs/L1_EVAL_REPORT.md`). 이 평가로 진짜 버그를 하나
잡았다 — 2글자 브랜드 코드(`nh` 등)에 대한 Levenshtein 거리 매칭이 TLD
자체(`.net`)까지 오탐시켜 정상 도메인 오탐률이 34%에 달했다. 고친 뒤엔
오탐률 1.88%(임계값 20)/0.05%(임계값 30)로 떨어졌다. 재현율은 이 범용
피싱 피드 기준 28~40%로 낮은 편인데, 이 피드가 대부분 국내 은행과 무관한
해외 범용 피싱(크립토 사기 등)이라 L1이 애초에 노리는 범위 밖이기 때문 —
`kb-bank-secure.tk`류 국내 브랜드 사칭 패턴은 여전히 75~95점으로 정확히
잡힌다. L2는 아직 이런 대규모 실측 평가를 하지 않았다.

L1 가중치 자체를 실제로 학습시키는 것(로지스틱 회귀 등, `scripts/train_l3_model.js`가
L3에 하는 것과 같은 방식)은 여전히 다음 단계로 남아 있다.

## 4. L3 융합 가중치도 실제 인간 데이터로 학습되지 않았다

`server/data/model/weights.json`의 기본값(`imu:0.5, traj:0.3, props:0.12,
timing:0.08`)은 원래 프로토타입에서 손으로 튜닝한 값 그대로다.
`scripts/train_l3_model.js`는 실제로 작동하는 학습·ablation·FPR@TPR95 파이프
라인이지만, 이 세션은 클라우드 컨테이너라 실제 사람이 폰을 들고 참여하는
데이터 수집을 물리적으로 수행할 수 없었다. `--synthetic` 플래그로 파이프라인
배관 자체는 검증했지만(`docs/L3_TRAINING_REPORT.md`), **그 결과는 진짜
평가가 아니다** — 인위적으로 분리 가능하게 만든 합성 데이터라 AUC 1.0이
나오는 게 당연하다. 실제 참여자 20~30명 데이터를 모아야 진짜 숫자가 나온다.

별도로 사용자가 이 프로젝트를 시작하기 전 직접 만든 예비 실험(데스크 vs
핸드헬드, accel spectrum + touch-triggered average + 세션별 결합비 3연 플롯)이
있다 — L3의 핵심 전제("진짜 터치는 IMU를 움직인다")를 뒷받침하는 실측 근거지만,
① 원격조작 조건이 아직 없고(정상 두 조건만 갈렸을 뿐, remote 라인이 없으면
최종 증거가 아님), ② 그 스크립트가 이 코드베이스의 `analyzeSession`과 같은
파이프라인으로 만들어졌는지 확인되지 않아 절대 임계값(`minPeakAbs` 등)을
직접 그 숫자로 옮기지는 않았다. 대신 11번 항목처럼 임계값 자체를 그 세션의
실제 탭 데이터로 자동 보정하도록 바꿔, 어느 쪽이든 틀린 상수를 또 하드코딩하는
실수를 피했다.

## 5. 서버가 "신뢰"하는 것은 텔레메트리의 형식이지, 출처가 아니다

`/api/session/decision`은 taps/imu/trace가 진짜 그 세션·그 기기에서 왔다는
것을 검증하지 않는다(스푿 테스트 시나리오 C 참고 — 브라우저 없이 직접 POST해도
동일하게 처리됨). 이건 설계상 의도된 분리다: 점수 계산과 텔레메트리 인증은
별개 문제이고, L4(흔들기 챌린지)가 최종 승인 지점이 되도록 만들었다. 하지만
챌린지 자체도 결국 클라이언트가 보고하는 IMU 샘플을 서버가 채점하는 구조라,
1번 항목의 위조 문제가 여기에도 그대로 적용된다.

## 6. 앱/권한 탐지는 범위 밖 (원래 기획서에도 명시된 한계)

브라우저는 다른 앱(AnyDesk, 접근성 서비스가 붙은 악성 APK)의 존재를
알 수 없다. MVP는 "금융 웹서비스 안에서의 세션 무결성 검증"으로 범위를
좁혔고, 앱 탐지는 네이티브 SDK가 필요한 별도 로드맵이다.

## 7. iOS

`DeviceMotionEvent.requestPermission()` 분기는 있지만 실기기 검증은 아직
안드로이드 크롬 기준으로만 해봤다. 흔들기(L4) 임계값은 처음엔 안드로이드
기준 절대값(13 m/s² → 7 m/s²)으로 하드코딩했다가 두 번 다 실제 기기에서
틀렸던 적이 있어서, 지금은 그 세션 자체의 최근 IMU 중앙값 대비 상대적으로
얼마나 튀었는지로 판정하도록 바꿨다(`server/src/app.js`의
`/api/session/challenge-result`). 기기·OS에 무관하게 동작하도록 설계는
했지만, 아이폰 실기기에서 실제로 검증하지는 못했다 — 여전히 확인이 필요하다.
L3의 터치–IMU 임펄스 신호(`analyzeSession`)도 마찬가지로 절대 m/s² 임계값이
아니라 세션 내 median/MAD 기반 z-score라 원리상 기기 독립적이지만, 이 역시
아이폰에서 직접 확인된 적은 없다.

## 8. 정지 상태 오탐(거치대 사용자)

IMU 신호 단독으로는 폰을 거치대에 놓고 쓰는 사람과 원격 조작을 구분할 수 없다.
현재 구조는 이를 완화하려고 여러 신호를 융합하고 최종 판단을 챌린지로 넘기지만,
"거치대 사용자에게 챌린지가 얼마나 자주 뜨는가"는 실측하지 못했다(위 4번과 동일한
이유 — 실사용자 데이터 부재). 다만 사용자가 직접 만든 예비 실험(4번 참고)에서는
책상에 놓인 폰도 터치 순간엔 날카로운 IMU 임펄스가 뜬다는 게 확인됐다 —
거치대/책상 사용자와 원격조작을 가르는 축은 "배경이 조용한가"가 아니라
"터치 임펄스가 있는가"이며, 그게 바로 `analyzeSession`이 이미 재는 것이다.
그래도 실제 오탐률은 여전히 측정된 적 없다.

## 9. 개인정보/동의

센서 데이터 수집(개발자 도구 안의 수집 화면)에 대한 동의 문구, 보관 기간, 삭제 절차가 없다.
`server/data/sessions/`는 인증 없이 누구나 쓸 수 있는 로컬 파일 저장소이고,
실제 참여자 데이터를 모을 때는 최소한 별도 동의 화면과 접근 제어가 필요하다.

## 10. 서명 키 관리

`server/src/sign.js`의 HMAC 비밀키는 환경변수가 없으면 하드코딩된 개발용
기본값을 쓴다(`dev-only-insecure-secret-replace-in-production`). 프로덕션
배포 전 반드시 `PRESENCE_SIGNING_SECRET`을 실제 비밀 관리 시스템에서 주입해야
한다.

## 11. L3 임펄스 임계값 자동 보정 — 이제 실제 아이폰 데이터로 검증됨

`minPeakAbs`(터치 임펄스로 인정할 최소 절대 크기)도 원래 안드로이드 기준으로
손으로 찍은 값(0.35 m/s²)이었다. `server/public/index.html`의
`tryAutoCalibrate()`가 세션 초반에 z-score 기준을 자체적으로 통과하는 진짜
탭이 5개 모이면 그 델타로 `minPeakAbs`를 그 세션·그 기기·그 쥐는 방식에
맞게 스스로 재설정한다. 별도 보정 화면 없이 이체 흐름 중 자연스러운 탭만으로
수렴한다.

사용자가 실제 아이폰으로 미리 수집해둔 13개 세션(3명, desk/handheld 조건,
`scripts/import_real_export.js`로 이 코드베이스 포맷으로 변환해 사용)으로
`scripts/validate_autocalibration.js`를 돌려 실측했다(`docs/
L3_REAL_DATA_VALIDATION.md`):

- 처음 버전(통과한 델타 5개의 **중앙값**×0.5)은 일부 세션에서 역효과가
  났다 — 초반에 우연히 강한 탭만 걸리면 임계값이 오히려 기본값보다
  높아져서, 그 뒤에 오는 진짜 약한 탭들을 더 많이 놓쳤다. 20번째
  백분위수×0.4로 바꾸니(같은 5개 수렴 조건, `server/public/index.html`에
  반영됨) 13개 세션 전부에서 기본값보다 나빠진 경우가 **0건**이었고,
  여러 세션에서 개선됐다.
- desk 조건 평균 impulseRatio 0.715 vs handheld 조건 0.293 — 사용자의
  예비 실험(4번 참고)이 보여준 물리("책상은 충격이 그대로 꽂히고, 손에
  들면 배경 흔들림 때문에 덜 도드라진다")가 실제 우리 검출기 위에서도
  그대로 재현됐다.
- **아직 열려 있는 문제**: 자동 보정은 13개 세션 중 7개에서만 수렴했고,
  handheld 조건에서는 7개 중 1개만 수렴했다 — 배경 흔들림 자체가
  z-score 게이트를 통과할 만큼 뚜렷한 임펄스를 만드는 경우가 드물어서다.
  즉 손에 들고 쓰는 조건에서는 자동 보정이 기본값에 계속 의존하게 되는
  경우가 많다는 뜻 — 완전히 해결된 게 아니라 실측으로 정확히 어디가
  남았는지 확인된 상태.

## 12. Vercel 배포의 L2 — 코드는 있지만 라이브로 검증 못 함

`server/src/l2.js`는 `process.env.VERCEL`을 감지해 로컬(`playwright` 풀
브라우저)과 서버리스(`playwright-core` + `@sparticuz/chromium`)를 분기한다.
널리 쓰이는 조합이라 동작할 가능성이 높지만, **이 세션에는 Vercel 계정이
없어 실제 배포 환경에서 한 번도 실행해보지 못했다.** 배포 후 링크검사
흐름에서 페이지가 실제로 렌더링되는지 반드시 확인할 것. 실패하더라도
`/api/l2/check`는 502를 반환할 뿐이라 L1·L3·L4는 영향받지 않는다 —
최악의 경우 "링크 판정 중 페이지 부분만 조용히 빠지는" 정도로 그친다.

## 13. Vercel 배포에서는 세션 수집(수집 도구)이 저장되지 않는다

서버리스 함수의 파일시스템은 읽기 전용이라 `/api/session/export`가 Vercel
환경에서는 저장을 시도하지 않고 바로 오류 메시지를 반환하도록 막아뒀다
(`process.env.VERCEL` 분기, `server/src/app.js`). 실제 데이터 수집은 폰을
직접 조작해야 하는 작업이라 어차피 로컬 워크플로였지만, 향후 공개 배포에서도
수집을 지원하려면 Vercel Blob/KV 같은 외부 저장소 연동이 필요하다.

## 14. L4 흔들기 챌린지 — 차량 진동 오인증 (수정됨, 잔여 갭 있음)

실사용자 제보: 차 안에서 통화하며 사기를 당하는 도중(보이스피싱의 흔한
실제 상황) 방지턱 하나만 넘어도 흔들기 챌린지가 통과되어 송금이
승인됐다. 원인은 `/api/session/challenge-result`(`server/src/app.js`)가
"기준선 대비 임계값을 넘는 샘플 개수"만 셌기 때문 — 60Hz 샘플링에서
~150ms짜리 방지턱 충격 한 번만으로도 6~9개 샘플이 한꺼번에 임계값을
넘어 `SHAKE_HITS_REQUIRED=3`을 그 자리에서 만족시켰다(고의로 흔든 적
없이).

**수정**: 원시 샘플 개수 대신 시간적으로 분리된 "burst" 개수를 센다
(`BURST_GAP_MS=150`ms 이상 간격이 벌어지면 새 burst로 카운트). 진짜
손 흔들기는 왕복 운동이 챌린지 구간 전체에 걸쳐 반복되므로 여러
burst를 만들지만, 방지턱 하나는 burst 하나뿐이다. 클라이언트
(`index.html`의 `openShake()` 진행률 표시)도 동일한 burst 로직으로
맞춰 서버 판정과 UI가 어긋나지 않게 했다.

**검증**: 직접 API 재현(방지턱 1회 → 이제 거부, `authorized:false`)과
실제 Playwright UI E2E(진짜 흔들기는 여전히 통과, 방지턱 패턴은 타임아웃
후 거부)로 확인했고, `server/test/spoof_test.js`에 회귀 테스트로
영구히 남겼다(시나리오 E).

**잔여 갭 (미해결, 정직하게 문서화)**: 방지턱이 하나가 아니라 험한
비포장길처럼 챌린지 구간(4초) 안에 서로 떨어진 방지턱을 3개 이상
넘으면, 그 각각이 독립된 burst로 잡혀 여전히 통과한다
(`spoof_test.js` 시나리오 F로 재현·문서화됨, `authorized:true`). burst
개수만으로는 "의도적으로 3번 흔든 것"과 "우연히 떨어진 방지턱 3개"를
구분할 수 없기 때문이다. 이를 완전히 막으려면 주파수 영역 분석이
필요하다 — 진짜 손 흔들기는 2~6Hz 대역에서 방향이 번갈아 바뀌는
진동인 반면 방지턱은 한 방향 단발 충격이라 신호 모양이 다르다. 이
프로젝트는 실측 데이터 없이 물리 센서 임계값을 새로 추측하지 않는다는
원칙을 지켜왔으므로, 이 분석은 실제 차량 주행 중 흔들기/방지턱
데이터를 확보하기 전까지는 구현하지 않고 이렇게 갭으로 남겨둔다.
